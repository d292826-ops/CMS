## План деплоя

1. Сохранить прежний код CMS в резервной ветке и определить предыдущую публикацию.
2. Восстановить зависимости `app/` строго из lockfile; выполнить тесты и сборку.
3. Добавить корневую команду сборки и конфигурацию существующего Sites;
   `scripts/build-static.mjs` собирает `app/` и помещает готовый сайт в `dist/`.
4. Передать все отслеживаемые материалы нашего проекта в CMS, сохранив историю
   прежнего репозитория. `.env`, `.tools`, зависимости, временные профили и копии БД не передавать.
5. В исходном репозитории Sites заменить прежний код согласованным снимком,
   собрать и упаковать его штатным помощником; сохранить и опубликовать новую версию.
6. Получить явное разрешение заменить VPS на ChatGPT Sites. Затем опубликовать
   уже сохранённую версию №3, дождаться подтверждения; проверить главную, основной цикл
   заявка → выдача → подтверждение → финансовый разбор и дашборды.
7. Сверить журналы, записать фактические коммиты, версию и ограничения в этот
   файл и `roadmap.md`. Не отмечать успешную публикацию до её проверки.

## Как обновить

- Автодеплой из GitHub не настроен; один `git push` не является публикацией сайта.
- Попросить Codex «Размести последние изменения». Сначала прочитать этот runbook.
- Проверить текущую опубликованную версию, источник и доступ сайта через Sites.
- Восстановить зависимости командой `npm --prefix app ci`; версии не повышать без отдельной необходимости.
- Выполнить `npm --prefix app test`, затем `npm run build` из корня.
- Открыть исходный репозиторий существующего сайта штатным помощником Sites,
  перенести проверенные исходники, собрать и упаковать их, сохранить и опубликовать версию.
- Передвигать `main` GitHub только от проверенного текущего коммита, без force push.
- Повторить smoke-test и записать результат. Перезапуск обслуживающего сервиса
  выполняет платформа Sites при публикации, отдельных SSH-команд нет.

## Как смотреть логи и диагностику

- Sites: состояние публикации и журнал Worker через инструменты Sites в Codex.
- Запрос от 24 ноября до замены CMS: только ошибки за 180 минут, возвращено 0 записей.
  Это результат ограниченного запроса, не доказательство отсутствия всех проблем.
- Локально: вывод терминала предпросмотра и консоль браузера; сообщения INFO / WARNING / ERROR.
- В текущем статическом MVP нет backend, общей БД, рабочего входа и миграций.
  Данные сохраняются отдельно в каждом браузере. Не использовать реальные сведения компании.

## Бэкапы

- Код: история GitHub и резервная ветка прежнего CMS, сохранённые версии Sites.
- Старые D1/R2: не удалены и не используются новым статическим демо.
- Состояние нового демо: localStorage текущего браузера, серверной резервной копии нет.
- Расписание и ротация автоматических копий демоданных не настроены.
- Восстановление исходного учебного набора — кнопка «Начать демонстрацию заново»
  с подтверждением. Это заменяет изменения только в текущем браузере.

## Что делать если упало

1. Проверить адрес, статус последней публикации и загрузку HTML/CSS/JS.
2. Если новая публикация неуспешна, проверить её сообщение об ошибке и журналы;
   не удалять данные браузера и не менять доступ сайта для обхода проблемы.
3. При регрессии опубликовать ранее сохранённую исправную версию Sites.
   Версия №2 содержит прежнюю систему CMS, её откат меняет продукт на старый.
4. Локально дважды нажать `app/Запустить сайт.command`; окно терминала оставить открытым.
5. После исправления повторить сборку и основной сценарий, записать результат и версию.
