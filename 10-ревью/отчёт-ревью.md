## 🟡 Желательно — лучше поправить

### 1. После сохранённой выдачи показано противоречивое сообщение

**Что происходит:** в контрольном примере потери ответа выдача сохраняется, остаток уменьшается. При этом сообщение одновременно говорит «Выдача сохранена» и «Списание не выполнено; … можно повторить».

**Где:** [app/src/pages/IssuePage.tsx](../app/src/pages/IssuePage.tsx), строка 7.

**Как исправить:** разделить ошибку сохранения и сбой отображения уже сохранённой операции. Во втором случае показывать только подтверждённое состояние и кнопку открытия документа.

Повторного списания при проверке не произошло, но текст вводит кладовщика в заблуждение. Затрагивает фичу №193 — уведомления об ошибках.

### 2. После сброса демонстрации остаётся ранее выбранный получатель

**Как воспроизвести:** выбрать получателя в форме выдачи → перейти в номенклатуру → вернуться на старт → сбросить демонстрацию → снова открыть эту выдачу. Старый получатель уже выбран, хотя документ ещё не создан.

**Где:** [app/src/pages/IssuePage.tsx](../app/src/pages/IssuePage.tsx), строка 2 — отдельное хранилище черновиков получателя; [app/src/state/DemoProvider.tsx](../app/src/state/DemoProvider.tsx), строка 48 — сброс его не очищает.

**Как исправить:** включить этот черновик в общий сброс демо и явно управлять его сохранением при переходах и смене участника.

Затрагивает фичи №10, №11 и №13.

### 3. Переход в номенклатуру стирает подсказки об остальных ошибках

**Как воспроизвести:** отправить пустую заявку — появляются три подсказки. Затем выбрать деталь через номенклатуру. После возвращения исчезают все подсказки, хотя машина и количество по-прежнему не заполнены.

**Где:** [app/src/ui/RequestForm.tsx](../app/src/ui/RequestForm.tsx), строка 3.

**Как исправить:** сохранять состояние проверки вместе с черновиком либо восстанавливать подсказки после возвращения из каталога.

Это прямое расхождение с критерием **88.4**: исправление одного поля должно оставлять подсказки у остальных ошибочных полей.

### 4. Предложенное восстановление после конфликта данных не работает

**Что происходит:** после изменения данных во второй вкладке первая показывает «Документ уже изменился. Откройте его заново». Закрытие и повторное открытие формы не помогает — ошибка повторяется. Помогает полная перезагрузка страницы.

**Где:** [app/src/state/commands.ts](../app/src/state/commands.ts), строка 12 и [app/src/state/DemoProvider.tsx](../app/src/state/DemoProvider.tsx), строка 26.

**Как исправить:** предложить работающую кнопку «Обновить данные» с повторной загрузкой состояния и проверкой черновика.

Одновременная работа нескольких вкладок не гарантируется текущим ТЗ. Замечание касается именно неработающей инструкции восстановления.

### 5. Не во всех формах ошибка связана с полем и получает фокус

**Что происходит:** при сохранении пустого пояснения расхождения появляется подсказка, но фокус не переходит к полю. У него отсутствуют `aria-invalid` и `aria-describedby`. У выбора получателя также отсутствует связь с текстом ошибки через `aria-describedby`.

**Где:** [app/src/pages/DocumentPage.tsx](../app/src/pages/DocumentPage.tsx), строка 8 и [app/src/pages/IssuePage.tsx](../app/src/pages/IssuePage.tsx), строка 7.

**Как исправить:** добавить связь подсказки с полем, признак ошибки и перевод фокуса на первое ошибочное поле.

Этого прямо требует раздел форм в [дизайн.md](../дизайн.md), строки 115–116.

- Текущий рабочий раздел в боковом меню не выделяется: состояние `active` предусмотрено только для начала демонстрации. На финансовом экране оба пункта выглядят неактивными.

**Где:** [app/src/styles/global.css](../app/src/styles/global.css), строка 3 и [app/src/ui/AppShell.tsx](../app/src/ui/AppShell.tsx), строка 9.

**Как исправить:** добавить недостающий параметр заголовка и определять активный пункт меню по текущему адресу, включая `aria-current`.

### 🔴 R2-1. Повторная подготовка возвращает прежнего получателя

**Статус:** новая регрессия после `143c182`, подтверждена в одной вкладке production-сборки. Блокирует положительное заключение по основному сценарию выдачи.

**Как воспроизвести:**

1. Выбрать кладовщика `K1` и открыть выдачу по исходной заявке.
2. Выбрать получателя `D1` и нажать «Подготовить документ».
3. Изменить получателя на `D2` и снова нажать «Подготовить документ».
4. Поле без предупреждения возвращается на `D1`.
5. Нажать «Подтвердить фактическую выдачу» → «Провести выдачу»: сохранённый документ проведён на `D1`.

Сценарий воспроизведён дважды. Это не связано с неподдерживаемой параллельной работой нескольких вкладок.

**Где:** [app/src/pages/IssuePage.tsx](../app/src/pages/IssuePage.tsx), строка 7; [app/src/domain/issue.ts](../app/src/domain/issue.ts), строка 40.

**Причина и последствия:** `prepareIssue()` для уже подготовленного документа возвращает старый документ с `changed: false`. Страница принимает результат за успешное сохранение уточнения, очищает черновик и подставляет прежний `recipient_user_id`. До `143c182` локальное состояние страницы удерживало новый выбор для последующего проведения. Теперь можно оформить фактическую выдачу не тому человеку, которого кладовщик явно выбрал при уточнении.

**Связь с ТЗ:** критерий **52.1** и возможность уточнять получателя до проведения — [техническое-задание.md](../техническое-задание.md), строка 1923.

**Как исправить:** обновлять получателя существующего `PREPARED`, сохраняя идентификатор документа, без складского движения и финансовой операции. Повтор с теми же реквизитами должен оставаться идемпотентным. Добавить проверку «подготовить на D1 → уточнить на D2 → повторно подготовить → провести на D2».

### 🟡 R2-2. Новый участник видит ошибки чужой пустой формы

**Статус:** новая регрессия после `143c182`.

**Как воспроизвести:** под `M1` отправить пустую заявку, получить ошибки машины, детали и количества. Через «Выбрать участника» переключиться на `D1` и открыть «Создать заявку». Все три ошибки уже отображаются до первого действия `D1`.

**Где:** [app/src/state/RequestDraft.tsx](../app/src/state/RequestDraft.tsx), строка 6; [app/src/App.tsx](../app/src/App.tsx), строка 45.

**Причина и последствия:** ошибки перенесены в общий провайдер и переживают уход со страницы. Пустые поля дают `dirty === false`, поэтому прямое переключение участника обходит `clear()`. Новый участник получает состояние проверки предыдущего участника.

**Связь с ТЗ:** изоляция контекста участника и начальное состояние формы; связанный пункт первого ревью — №3.

**Как исправить:** очищать состояние проверки после каждой успешной смены участника, включая пустую отклонённую форму, либо связывать черновик и ошибки с конкретным участником. Проверять смену участника не только при наличии заполненных полей.

### 🟡 R2-3. Замена одного недопустимого количества другим снимает подсказку
